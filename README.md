# Граф на основе разреженной матрицы смежности

## Идея проекта

Необходимо реализовать собственную структуру данных для работы с графами. Граф будет состоять из множества вершин и рёбер, которые соединяют эти вершины. При этом у ребра должны быть не только начальная и конечная вершины, но и некоторые данные — в первую очередь вес.

Основная задача — выбрать способ хранения графа и реализовать на его основе несколько алгоритмов:

- поиск минимального остовного дерева;
- поиск максимального остовного дерева;
- топологическую сортировку вершин ориентированного графа.

Также понадобятся базовые операции с графом: добавление и удаление вершин и рёбер, проверка существования ребра, получение его веса и поиск соседних вершин. Дополнительно планируется реализовать обходы в ширину и глубину.

## 1. Как хранить граф

Самый очевидный вариант — матрица смежности. Если в графе `n` вершин, можно создать матрицу `n × n`, где ячейка `(i, j)` будет показывать, есть ли ребро между вершинами `i` и `j`.

Но у такого подхода есть недостаток: даже если рёбер мало, память всё равно выделяется под все `n²` ячеек. Для разреженного графа, в котором существует только небольшая часть возможных рёбер, большая часть матрицы окажется пустой.

Поэтому я хочу использовать **разреженное представление матрицы смежности**. Логически это всё ещё матрица, но физически храниться будут только её заполненные ячейки, то есть существующие рёбра.

Для этого подойдёт словарь:

- **ключ** — пара вершин `(u, v)`, задающая положение ребра в матрице;
- **значение** — объект ребра с его данными, например весом.

Например, для графа с рёбрами `A — B` веса `4` и `B — C` веса `7` в словаре будут находиться только две записи:

```text
(A, B) -> Edge{weight = 4}
(B, C) -> Edge{weight = 7}
```

Если ключа `(A, C)` нет, значит, соответствующего ребра не существует. Таким образом, не понадобится отдельно хранить признак существования ребра: его определяет наличие ключа в словаре.

В результате для хранения вершин и рёбер потребуется память порядка `O(V + E)`, где `V` — количество вершин, а `E` — количество существующих рёбер, вместо `O(V²)` для обычной матрицы.

## 2. Ориентированный и неориентированный граф

Хочется, чтобы одна реализация поддерживала оба типа графов.

В **ориентированном графе** пары `(u, v)` и `(v, u)` обозначают разные рёбра, поэтому порядок вершин в ключе важен.

В **неориентированном графе** ребро между `u` и `v` не зависит от направления. Чтобы не хранить одно и то же ребро дважды, можно договориться всегда располагать вершины в ключе в определённом порядке. Например, если `v < u`, менять их местами. Тогда запросы `(u, v)` и `(v, u)` будут обращаться к одной записи словаря.

Тип графа я планирую задавать на этапе компиляции с помощью булевого шаблонного параметра `directed_`. По умолчанию граф будет неориентированным.

## 3. Какие структуры данных понадобятся

Чтобы граф не зависел от одного конкретного типа данных, сделаю его шаблонным.

### Вершина

Для вершины будет отдельная структура `GraphNode<T>`, которая хранит значение типа `T`. Понадобятся операции сравнения вершин: они нужны, в частности, для ключей словаря и проверки существования вершины.

### Ребро

Для ребра будет структура `GraphEdge<E>`, где `E` — тип веса. Пока достаточно одного поля `weight`, но отдельный тип ребра позволит в дальнейшем добавлять другую информацию, не меняя общую идею хранения графа.

### Словарь

Сам граф не должен быть жёстко привязан к конкретной реализации словаря. Я задам требования к нему через концепт `SpecDictionary`.

От словаря будут нужны четыре операции:

- `has_key(key)` — проверить существование ключа;
- `add(key, value)` — добавить запись;
- `erase(key)` — удалить запись;
- `get(key)` — получить значение по ключу.

В качестве реализации словаря можно использовать собственное `avl_tree`. Важно, чтобы граф взаимодействовал со словарём только через перечисленные операции.

### Хранение вершин

Отдельно от словаря рёбер буду хранить последовательность всех вершин в `ArraySequence<NodeType>`. Это необходимо, поскольку в графе могут быть изолированные вершины, которые не встречаются ни в одном ребре.

В итоге основная структура будет выглядеть примерно так:

```cpp
template <typename Dict, typename NodeType, typename EdgeType,
          bool directed_ = false>
class Graph;
```

Внутри неё будут два основных поля:

```cpp
Dict matrix_;                       // существующие рёбра
ArraySequence<NodeType> vertices_; // все вершины графа
```

Ключом `matrix_` станет `std::pair<NodeType, NodeType>`.

## 4. Базовые операции с графом

Сначала реализую методы, которые позволят создавать и изменять граф:

- `add_vertex` / `remove_vertex` — добавление и удаление вершины;
- `add_edge` / `remove_edge` — добавление и удаление ребра;
- `has_vertex` / `has_edge` — проверка существования вершины или ребра;
- `get_edge` — получение веса ребра;
- `get_vertices` — получение всех вершин;
- `get_neighbors` — получение вершин, смежных с заданной.

При добавлении ребра буду автоматически добавлять его концевые вершины, если их ещё нет. Если ребро с таким ключом уже существует, его вес можно обновить.

При удалении вершины необходимо также удалить все инцидентные ей рёбра. Для ориентированного графа это и входящие, и исходящие рёбра.

Метод `get_edge` удобно сделать возвращающим `std::optional<E>`. Так можно отличать отсутствие ребра от ребра с нулевым весом.

Для получения соседей на первом этапе достаточно пройти по всем вершинам и проверить наличие соответствующего ключа в словаре. Это не самый быстрый вариант для сильно разреженных графов, зато не потребует вводить дополнительное хранилище списков смежности.

## 5. Поиск минимального и максимального остовного дерева

После базовых операций можно перейти к остовным деревьям.

**Остовное дерево** связного неориентированного графа должно содержать все его вершины, не иметь циклов и состоять ровно из `V - 1` рёбер.

Мне нужны два варианта:

- **минимальное остовное дерево** — с наименьшей суммой весов рёбер;
- **максимальное остовное дерево** — с наибольшей суммой весов рёбер.

Для обоих случаев планирую использовать **алгоритм Прима**. Делать две независимые реализации необязательно: логика построения будет одинаковой, изменится только правило выбора лучшего ребра.

Алгоритм будет работать следующим образом:

1. Выбрать начальную вершину и считать её добавленной в строящееся дерево.
2. Для каждой ещё не добавленной вершины хранить лучшее найденное ребро, соединяющее её с уже построенной частью дерева.
3. Выбрать среди этих кандидатов ребро минимального веса (или максимального для второго варианта).
4. Добавить выбранное ребро и новую вершину в дерево.
5. Повторять, пока все вершины не будут включены в остов.

Для кандидатов можно завести небольшую вспомогательную структуру: признак включения вершины в дерево, индекс её родителя и текущий лучший вес. Отсутствие найденного ребра удобно обозначать через `std::optional<E>`.

Общую логику вынесу во внутренний метод `spanning_tree(bool maximum)`, а наружу предоставлю два понятных метода: `minimum_spanning_tree()` и `maximum_spanning_tree()`.

Оба метода будут доступны только для неориентированного графа. Если граф несвязный, построить одно остовное дерево для всех его вершин нельзя, поэтому в этом случае будет выбрасываться исключение.

Также добавлю `total_edge_weight()`, чтобы можно было получить суммарный вес рёбер построенного дерева и сравнить результаты.

## 6. Топологическая сортировка

Для ориентированного графа хочу реализовать топологическую сортировку — такой порядок вершин, при котором для каждого ребра `u -> v` вершина `u` стоит раньше вершины `v`.

Топологический порядок существует только для **ориентированного ациклического графа (DAG)**.

Для реализации выберу **алгоритм Кана**:

1. Для каждой вершины подсчитать входящую степень — число рёбер, которые в неё входят.
2. Поместить все вершины с нулевой входящей степенью в очередь.
3. Пока очередь не пуста, извлекать из неё вершину и добавлять её в результат.
4. Для всех исходящих из неё рёбер уменьшать входящую степень соответствующих соседей.
5. Если у соседа входящая степень стала равна нулю, добавлять его в очередь.

Для хранения степеней можно использовать `avl_tree<NodeType, int>`, для очереди — собственную `Queue<T>`, а для результата — `ArraySequence<T>`.

В конце необходимо проверить количество обработанных вершин. Если оно меньше общего числа вершин, значит, в графе есть цикл и корректную топологическую сортировку получить нельзя. В таком случае метод `topological_sort()` будет выбрасывать исключение.

Этот алгоритм имеет смысл только для ориентированных графов, поэтому доступность метода также ограничу на этапе компиляции.

## 7. Дополнительные обходы графа

Помимо основных алгоритмов, хочу добавить стандартные обходы:

**BFS (поиск в ширину).** Буду использовать собственную `Queue<T>`: сначала посещается стартовая вершина, затем её соседи, потом соседи этих соседей и так далее.

**DFS (поиск в глубину).** Для итеративной реализации буду использовать собственный `Stack<T>`: переходить к ещё не посещённым соседям, пока это возможно, затем возвращаться к оставшимся вариантам.

В обоих обходах нужно отмечать уже посещённые вершины. Для этого подойдёт `avl_tree<NodeType, bool>`. Порядок обхода буду возвращать в `ArraySequence<T>`.

## 8. Что важно учесть

Поскольку матрица будет храниться в словаре, стоимость обращения к ребру зависит от операций этого словаря. Например, при использовании AVL-дерева поиск, вставка и удаление ключа занимают `O(log E)` в обычной оценке для непустого словаря.

При этом метод поиска соседей будет проверять все вершины, а алгоритмы построения остова и топологической сортировки тоже будут использовать перебор вершин. То есть экономия памяти за счёт разреженного хранения сама по себе не означает, что все алгоритмы будут работать за время `O(V + E)`.

Для сравнения весов в остовных деревьях тип `E` должен поддерживать упорядочивание. Для подсчёта общей суммы весов дополнительно понадобится операция `+=`.

## План работы

1. Описать типы вершины и ребра, а также требования к словарю.
2. Создать шаблонный класс графа с отдельным хранением вершин и разреженной матрицей рёбер.
3. Реализовать добавление, удаление и получение данных о вершинах и рёбрах.
4. Добавить BFS и DFS на собственных очереди и стеке.
5. Реализовать алгоритм Прима для минимального и максимального остовов.
6. Реализовать топологическую сортировку алгоритмом Кана.
7. Написать тесты для ориентированных и неориентированных графов, пустых и несвязных графов, циклов, изолированных вершин и рёбер с нулевым весом.

**Итоговая цель** — получить универсальную шаблонную реализацию графа, которая не зависит от конкретного словаря, хранит только существующие рёбра и позволяет запускать основные алгоритмы без использования стандартных контейнеров для организации обходов и хранения вершин.
